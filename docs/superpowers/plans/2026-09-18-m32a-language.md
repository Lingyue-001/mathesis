# M3.2A canonical ontology and language layer

**Goal:** Translate established backend facts without altering interpretation, execution, action legality or layout.
**Baseline:** c3e5d2d. User-specified architecture is approved: typed codes → one backend registry → presentation → API → Workbench/reference.

## Inventory and boundaries

Inventory uses imported GRAMMAR/EXACT, OPERATION_CONTRACTS, ACTIONS,
QUANTITY_UNITS, UNIT_QUANTITY_KINDS and actual corpus service results; never
source-string scraping. Two exposed procedures currently emit 9 event kinds,
14 syntax kinds, 3 question kinds; stale replay adds stale_session.
The existing JavaScript names table and raw enum rendering are duplicate
presentation owners and will be removed. Overlapping candidate_options are
nearby evidence, not certified alternatives.

- `analysis_parser/ontology.py`: single backend vocabulary, definitions,
  hierarchy, required fact fields and forbidden inferences. No execution rules.
- `workbench/presentation.py`: read-only fact-to-language projection and
  reference export. Unknown visible codes fail explicitly.
- Existing service/API and JS renderers consume the view model; no label maps
  in JavaScript. New reference page uses existing site classes and same API.
- Existing session action enumeration references the registry; parser grammar,
  IR, operation signatures and executor behavior remain unchanged.
